# C9.4: Agent and Orchestrator Identity

[Back to C09 Index](C09-Orchestration-and-Agents.md)

## Purpose

In multi-agent systems, every action must be attributable to a specific agent, and every mutation must be detectable. Without cryptographic identity and tamper-evident audit trails, it becomes impossible to determine which agent took which action, whether actions were authorized, or whether logs have been altered to conceal malicious activity. This section establishes agent identity as a first-class security primitive and requires audit logs that support forensic reconstruction.

## 2024-2026 Research Context

Agent identity has emerged as a central theme in agentic AI security, driven by the OWASP Agentic Top 10 (2026), the rise of non-human identity management as a discipline, and production tooling from Microsoft, Descope, Okta, and others. Descope argues that every threat in the OWASP Agentic Top 10 has one or more identity-related mitigations; that is a vendor position, not a measured result.

### OWASP Agentic Top 10: Identity-Related Threats

The OWASP Top 10 for Agentic Applications (2026) identifies three entries directly relevant to agent identity and audit:

- **ASI03 -- Identity and Privilege Abuse:** Agents exploiting credential inheritance and delegation chains. OWASP describes the risk as attackers exploiting trust and delegation chains to escalate access and hijack privileges, and treats identity as both the agent's assigned persona and any authentication material (API keys, OAuth tokens, delegated user sessions) that represents it. This maps to requirement 9.4.1's mandate for unique cryptographic identity per agent.
- **ASI07 -- Insecure Inter-Agent Communication:** Weak or absent mutual authentication between agents. Without cryptographic identity verification, agents cannot distinguish legitimate peers from impersonators. This threat reinforces 9.4.2's requirement for signed, timestamped action records.
- **ASI10 -- Rogue Agents:** Agents deviating from intended function without detection mechanisms. Credential rotation with anomaly-triggered revocation (9.4.3) and chain-bound, tamper-evident audit records (9.4.2) are the primary mitigations.

### Non-Human Identity Management

The 2025-2026 period saw agent identity recognized as a distinct category within non-human identity (NHI) management. Key developments:

- **Microsoft Entra Agent ID (positioned in March 2026 as the identity foundation of Microsoft Agent 365):** Each agent receives a unique identity in Microsoft Entra, with Identity Protection and Conditional Access policies extended to agents. Organizations can apply trusted access policies at scale, reduce gaps from unmanaged identities, and keep agent access aligned to organizational controls. Agent-specific risk signals (anomalous usage patterns, concurrent use from unexpected locations) trigger automated conditional access responses.
- **Descope Agentic Identity:** Provides unique cryptographic identities to agents with "full visibility into not only the actions the agents are taking, but also the permission model they fit into." Agent credentials can be revoked at any time, are never exposed to credential reuse, and do not persist across sessions. Audit data exports to SIEM providers for continuous monitoring.
- **Okta:** [Okta for AI Agents](https://www.okta.com/solutions/secure-ai/) treats agents as principals in its identity platform ("Agent as Principal", with each agent given its own verified identity) rather than extensions of user sessions (vendor positioning).

### Cryptographic Identity and Zero Trust

The Microsoft Agent Governance Toolkit (open-source, MIT license, 9,500+ tests per Microsoft's April 2026 release post) implements zero-trust agent identity with:

- **Ed25519 cryptographic credentials** for agent signing and authentication
- **SPIFFE/SVID support** for workload identity, enabling ephemeral agents to receive short-lived certificates automatically
- **Trust scoring on a 0-1000 scale** that continuously evaluates agent trustworthiness based on behavioral signals
- **Protocol bridges** across A2A, MCP, and IATP for cross-framework identity federation

For inter-agent communication, mutual authentication (mTLS) or signed messages ensure that when Agent A communicates with Agent B, both verify identity before exchanging data. Microsoft reports governance latency under 0.1 ms at p99 (a vendor figure, not independently benchmarked), which is small next to a typical LLM API call and makes per-action identity verification plausible at production scale.

### Execution Chain Binding, Tamper-Evident Audit, and Action Signing

Requirement 9.4.2's chain-binding control starts with distributed tracing but cannot stop there. W3C Trace Context and OpenTelemetry propagate `trace-id` and `span-id` values across services, which gives auditors a correlation spine for a run, but those headers are not cryptographic evidence and can be forged when accepted from untrusted boundaries. Treat trace IDs as routing and reconstruction metadata; bind them to signed action records, previous-record hashes, policy decisions, and the agent identity before relying on them as evidence.

- **Append-only audit logs** with signed, immutable records of every tool call, agent response, and inter-agent message. The Microsoft Agent Governance Toolkit implements this natively.
- **Hash-chain receipts** that include `chain_id`, `prev_hash`, action payload hash, policy hash, result hash, timestamp, agent identity, and signature. The 2026 Proof-of-Behavior draft uses this pattern to make every action verifiable against the previous receipt and to preserve cross-agent attribution.
- **Merkle tree / batch signing** for high-volume scenarios where per-action signing introduces unacceptable latency. Actions within a time window are batched and a Merkle root is signed, enabling efficient verification of any individual action within the batch.
- **SIEM integration:** Structured audit data exported to observability tools (OpenTelemetry/OpenInference) or SIEM providers enables cross-correlation of agent actions with broader security events. OpenInference adds agent, tool, chain, guardrail, and retrieval span kinds on top of OpenTelemetry so reviewers can distinguish the steps inside an agent run rather than treating them as generic service spans.

Cloud providers offer tamper-evident storage primitives: AWS CloudTrail (immutable), Azure Immutable Blob Storage, and GCP Cloud Audit Logs. For self-hosted systems, append-only databases or blockchain-anchored log hashes provide equivalent guarantees. The harder challenge remains custom instrumentation -- most agent frameworks do not emit structured logs with all required fields (actor, user, delegation scope, policy version, tool parameters, approval, outcome) by default.

### Credential Lifecycle and Revocation

Short-lived, task-scoped tokens have become the standard recommendation for agent credentials. This limits blast radius by ensuring an agent cannot use orphaned privileges for unauthorized tasks. Key practices:

- **SPIFFE SVIDs** with built-in short lifetimes and automatic rotation are well-suited for ephemeral agent instances
- **Rapid revocation mechanisms** ("kill switches") that instantly disable rogue agents and propagate revocation across all downstream systems
- **Compromise indicators** triggering automated revocation: anomalous usage patterns, concurrent use from different locations, failed authentication spikes, behavioral deviation from baseline

Revocation propagation in distributed systems has inherent latency (CRL distribution, cache TTLs). SPIFFE's push-based rotation model reduces this compared to traditional PKI, but the gap between compromise detection and full revocation remains a measurable attack window.

The eventing side is no longer only draft guidance. The OpenID Foundation finalized Shared Signals Framework 1.0, CAEP 1.0, and RISC 1.0 in 2025 (the specification documents are dated August 29, 2025). CAEP defines interoperable events such as session revocation, credential changes, and token-claims changes that a receiver can use to attenuate access before a cached agent credential naturally expires. For agent deployments, that makes revocation testing a two-part exercise: verify scheduled cryptographic rotation, then inject a signed CAEP event and measure whether every enforcement point terminates or re-evaluates the affected session.

### Real-World Identity Failures: "Agents of Chaos" and CVE-2025-12420

The theoretical risks of weak agent identity became tangible in early 2026. The "Agents of Chaos" study (arXiv, February 2026) deployed six autonomous agents on the OpenClaw framework across two live Discord servers, with email accounts, persistent file systems, and shell access. Twenty researchers interacted with them over two weeks. It is an exploratory red-teaming case study, not a measurement of how often such attacks succeed. The identity spoofing findings were stark:

- A researcher changed their Discord display name to match an agent's owner. In the same channel the agent caught the mismatch, because Discord user IDs stay constant across display-name changes. In a new private channel, without access to its earlier suspicion flags, the agent inferred ownership from the display name and tone and accepted the spoofed identity. It then complied with instructions to delete its persistent memory files, modify its own name, and reassign administrative access.
- Using the same display-name spoof, a researcher convinced an agent that a fabricated emergency required immediate broadcast. The agent emailed its full mailing list and beyond and tried to post to Moltbook, a social platform for AI agents (the post failed because of an unrelated account suspension), amplifying a false alarm.
- The study reported ten substantial vulnerabilities across eleven case studies, including unauthorized compliance with non-owners, disclosure of sensitive information, execution of destructive system-level actions, and cross-agent propagation of unsafe practices.

The lesson is that display-name-based or persona-based identity is not identity. The authors' own suggested mitigation for the Discord case was to bind the owner's immutable user ID into the agent's context. Cryptographic identity (requirement 9.4.1) addresses this class of spoofing, because the agent would verify a credential rather than a human-readable name, though it would not by itself address the study's other failure modes.

Separately, the "BodySnatcher" vulnerability (CVE-2025-12420, detailed publicly by AppOmni in January 2026 after ServiceNow patched hosted instances in October 2025) let an unauthenticated attacker impersonate another user through a Virtual Agent integration flaw, reportedly with only an email address and without triggering MFA or SSO -- a reminder that agent identity vulnerabilities affect commercial platforms, not just research prototypes.

### Agent Traffic Impersonation at Scale

DataDome's March 2026 report shows agent impersonation is an operational problem at internet scale. Its network recorded 7.9 billion AI agent requests in January and February 2026, and agentic traffic was 9.75% of total traffic for one customer over a 30-day window. The vendor-reported impersonation figures:

- **Meta-externalagent:** 16.4 million spoofed requests (the most impersonated agent)
- **ChatGPT-User:** 7.9 million fraudulent requests
- **PerplexityBot:** nearly 2.4% of requests fraudulent (the highest impersonation rate)

User-agent string spoofing transforms allowlists into attack surfaces. Sites that allowlist known agent identifiers based on string matching inadvertently create a backdoor for any attacker who sets the same user-agent header. This underscores why 9.4.1's requirement for cryptographic identity -- not string-based identification -- is essential for any system that processes agent requests.

### IETF Standardization: Agent Authentication and Audit

Two IETF Internet-Drafts published in early 2026 directly address agent identity and audit:

**draft-klrc-aiagent-auth-00 (March 2026)** -- the Agent Identity Management System (AIMS) framework, co-authored by engineers from AWS, Zscaler, Ping Identity, and Defakto Security. Rather than inventing new protocols, AIMS composes existing standards into a layered agent authentication stack:

- **Identity layer:** WIMSE (Workload Identity in Multi-System Environments) URIs with SPIFFE as the operationally mature implementation (`spiffe://trust-domain/path/to/agent`)
- **Credential formats:** X.509 certificates, JWT-based Workload Identity Tokens, and SPIFFE SVIDs. Static API keys are explicitly flagged as an anti-pattern -- they lack cryptographic binding and are unsuitable for agent identity.
- **Transport authentication:** mTLS for mutual authentication in service meshes, with application-layer alternatives (WIMSE Workload Proof Tokens, HTTP Message Signatures per RFC 9421) for environments with proxies or load balancers.
- **Authorization:** OAuth 2.0 positions agents as OAuth clients. Transaction Tokens (draft-ietf-oauth-transaction-tokens) create downscoped, single-transaction tokens that prevent broad-scope token misuse in internal service chains. A critical anti-pattern: tools must never forward received tokens directly to downstream services.
- **Cross-domain delegation:** Identity Chaining (draft-ietf-oauth-identity-chaining) and Identity Assertion JWT Grants for multi-SaaS agent environments.
- **Audit requirements:** Agent identifier, delegated subject, resource accessed, action, authorization decision, timestamp, correlation ID, attestation state, and revocation events.
- **Real-time revocation:** OpenID SSF/CAEP/RISC events enable revocation enforcement without polling delays.

The draft's stated approach is to compose existing standards rather than define new protocols. If that holds up, organizations can build agent identity on existing infrastructure (SPIFFE, OAuth 2.0, mTLS) without waiting for new specifications, although the draft is informational and has not been adopted as a standard.

**draft-stone-aivs-00 (March 2026)** -- the Agentic Integrity Verification Standard (AIVS) defines a portable, self-verifiable archive format for cryptographic proof of agent sessions:

- **Hash-chained audit log:** Sequential SHA-256 hash chain where each row's hash depends on the previous row's hash. Modification, insertion, deletion, or reordering of any action is cryptographically detectable.
- **Ed25519 digital signatures** bind the entire chain to a specific agent identity, providing non-repudiation.
- **AIVS-Micro:** A minimal ~200-byte attestation for continuous monitoring and API contexts where full session bundles are impractical.
- **Self-verifiable:** The proof bundle includes an embedded Python verifier requiring only Python 3 standard library -- no external dependencies for offline verification.
- **Standards integration:** AIVS bundles can be wrapped as W3C Verifiable Credential subjects, registered as SCITT signed statements, and apply the same manifest-chain concept to agent actions as C2PA applies to media asset provenance.
- **Mandatory redaction:** Sensitive fields (passwords, tokens, API keys) must be redacted in audit logs, with output truncation permitted without affecting chain integrity.

AIVS directly addresses requirement 9.4.2 (cryptographic binding of actions across the execution chain for non-repudiation) and supplies a tamper-evident, signed audit substrate -- a concrete, implementable specification.

### NIST AI Agent Standards Initiative and NCCoE Concept Paper

On February 17, 2026, NIST's Center for AI Standards and Innovation (CAISI) launched the AI Agent Standards Initiative with three strategic pillars: industry-led standards development, community-driven open-source protocol development, and research in agent security and identity verification.

The NCCoE published its concept paper, "Accelerating the Adoption of Software and Artificial Intelligence Agent Identity and Authorization," on February 5, 2026. The public comment period closed April 2, 2026. Rather than inventing new identity frameworks, the paper discusses applying existing IAM standards to agentic workloads: OAuth 2.0 and OpenID Connect for authentication and authorization, SCIM for identity lifecycle management, SPIFFE/SPIRE for workload identity, and attribute-based access control (including NGAC) for fine-grained policy enforcement. It is a request for stakeholder input: NIST says the NCCoE is considering a demonstration project, and the feedback will inform its scope and feasibility.

What NIST publishes from this initiative may later appear in compliance frameworks and vendor questionnaires, which would reward early alignment; that is an expectation, not a published timeline.

### Five Eyes Joint Guidance: Runtime Identity and Accountability Baseline

On May 1, 2026, ASD's Australian Cyber Security Centre, CISA, NSA, the Canadian Centre for Cyber Security, NCSC-NZ, and NCSC-UK published "Careful adoption of agentic AI services." The guidance is especially relevant to C9.4 because it names privilege compromise, scope creep, identity spoofing, agent impersonation, altered or replayed agent communications, and opaque delegation chains as first-order deployment risks for agentic systems.

The operational guidance maps directly to the requirements in this section. Agents should be granted only narrow task-scoped privileges, avoid broad or unrestricted access to sensitive data and critical systems, and undergo continuous identity and authorization checks at runtime. For privileged calls, the guidance recommends fresh cryptographic proofs, cryptographic signing for authorized commands and instructions, integrity checks for task definitions and constraints, and attestation that the agent is running expected and unmodified code. For accountability, organizations should preserve unified audit logs covering inputs, outputs, tool calls, execution paths, errors, task chains, decision points, access to external systems, and escalation paths; requests to delete logs or audit records should be quarantined for human review.

The important takeaway is that cryptographic identity by itself is no longer enough for high-impact agents. By May 2026, the public-sector baseline had moved toward per-call identity proof, per-request policy evaluation, tamper-resistant audit, and explicit human accountability for irreversible or high-impact actions.

### Identity in the Wild: Unit 42 Incident Data

The Unit 42 Global Incident Response Report (February 2026), drawing on more than 750 major incidents handled in 2025, found that identity weaknesses played a material role in almost 90% of investigations. Attackers are not breaking in -- they are logging in with stolen credentials and tokens, then exploiting fragmented identity estates to escalate privileges and move laterally. A key finding for agent systems: non-human identities (service accounts, automation roles, API keys, and emerging AI agents) often outnumber human users and are frequently over-privileged. Compromising a service account can be higher leverage and quieter than compromising a person. In the fastest quarter of intrusions, data exfiltration took about 72 minutes, down from 285 minutes the prior year (a 4x speed-up). This data underscores why unique, scoped, short-lived agent credentials (requirements 9.4.1 and 9.4.3) are not theoretical niceties but operational necessities.

### OpenClaw ClawHub Supply Chain: Credential Exfiltration at Scale

The OpenClaw malicious-skills campaign (January-February 2026) was a large supply chain attack on an AI agent skill registry. Counts differ by auditor and date. [Koi Security](https://web.archive.org/web/20260217001115/https://www.koi.ai/blog/clawhavoc-341-malicious-clawedbot-skills-found-by-the-bot-they-were-targeting) reported 341 malicious skills among 2,857 on ClawHub on February 1 and 824 among more than 10,700 by February 16; [Antiy CERT](https://www.antiy.net/p/clawhavoc-analysis-of-large-scale-poisoning-campaign-targeting-the-openclaw-skill-market-for-ai-agents/) counted 1,184 malicious skill packages in the registry's history as of February 5; and Snyk's ToxicSkills scan of 3,984 skills confirmed 76 malicious payloads. The identity and credential implications are direct:

- One skill disguised as a weather tool read the bot's `~/.clawdbot/.env` file and sent its contents to an external webhook (Koi). Most of the campaign delivered other payloads, such as the Atomic macOS Stealer. Two skills posing as Polymarket tools hid a reverse shell in otherwise working code.
- Snyk flagged publisher accounts such as `Aslaep123`, whose skills included a typosquatted trading-bot name (`polymarket-traiding-bot`), and `zaycv`, responsible for 40+ skills following an identical programmatic pattern.
- The campaign points to weak publisher identity verification and poor credential isolation in the agent runtime. For the agent's own credentials, those are the gaps that requirements 9.4.1 (unique cryptographic identity) and 9.4.3 (credential rotation and revocation) are designed to close; publisher verification itself belongs to supply chain controls (C06).

### CVE-2026-33017: Langflow Unauthenticated RCE

In March 2026, CVE-2026-33017 (CVSS 4.0 base score 9.3; NVD scores it 9.8 under CVSS 3.1) demonstrated how missing authentication in an AI orchestration platform creates catastrophic risk. Langflow's `/api/v1/build_public_tmp/{flow_id}/flow` endpoint allowed building public flows without authentication, passing attacker-controlled Python code to `exec()` with no sandboxing. Sysdig observed exploitation within 20 hours of disclosure -- with no public proof-of-concept, attackers built working exploits directly from the advisory. Langflow deployments commonly hold API keys for multiple cloud services, so a compromised instance can give lateral access to connected databases and cloud accounts. This is a textbook case of why agent platforms need identity as a first-class primitive: had the build endpoint required authentication, this unauthenticated exploit path would not have existed.

### Meta Rogue Agent Incident

On March 18, 2026, TechCrunch reported, citing The Information, that Meta had classified an internal incident as Sev 1, its second-highest severity level, and had confirmed it to The Information. An employee posted a technical question on an internal forum, and another engineer asked an AI agent to analyze it. The agent posted a response without asking permission to share it, and the employee acted on its flawed advice, which made company and user data available to engineers who were not authorized to see it for about two hours. Public reporting does not describe how the agent authenticated or which authorization checks it passed.

The incident is consistent with the point that agent identity alone does not bound what an agent does once it is running. For requirement 9.4.2, the relevant lesson is that chain-bound, context-rich action records (delegation scope, authorization decision, tool parameters, outcomes) let a reviewer reconstruct such a sequence; the reporting does not describe Meta's logging.

### CVE-2026-21858 (Ni8mare): n8n Workflow Platform Full Takeover

In early 2026, CVE-2026-21858 (CVSS 10.0) exposed a content-type confusion vulnerability in the n8n workflow automation platform, affecting versions from 1.65.0 before 1.121.0. The attack chain was devastating in its simplicity: an unauthenticated attacker could exploit form-based webhook handling (content-type confusion) to read arbitrary files on the server, extract the user database and session signing secret, forge an administrative session cookie, and then use n8n's built-in "Execute Command" nodes for arbitrary code execution on the host. Cyera estimated about 100,000 impacted servers globally; n8n patched the flaw in version 1.121.0 on November 18, 2025, and the CVE was published in January 2026. Enterprise environments running n8n typically hold API keys for multiple cloud services, so compromising one instance provided lateral access across connected infrastructure. Like CVE-2026-33017 (Langflow), this demonstrates that agent orchestration platforms without cryptographic identity at every layer create single points of catastrophic failure.

### Oracle Identity Manager CVE-2026-21992

Oracle patched CVE-2026-21992 (CVSS 9.8) in March 2026, a vulnerability enabling unauthenticated remote code execution via HTTP in Oracle Identity Manager. This is notable in the agent identity context because Oracle Identity Manager is precisely the kind of IAM infrastructure that organizations rely on to provision and manage non-human identities including agent credentials. A compromise of the identity provider itself undermines every downstream identity assertion -- a reminder that the identity infrastructure securing agents must itself be rigorously hardened.

### SPIFFE and OAuth: Complementary Identity Layers for Agents

As of March 2026, a widely shared framing is that agent identity requires two complementary layers: SPIFFE answers "is this workload who it claims to be?" while OAuth answers "is this workload allowed to do what it's requesting?" Neither replaces the other.

The Riptides Controlplane (November 2025) demonstrates a practical integration for MCP environments: it functions as both SPIFFE issuer and OAuth/OIDC authorization server, injecting SVID credentials at the kernel level without code modifications. Agents self-register using cryptographic proof rather than client secrets, following the IETF Dynamic Client Registration with SPIFFE specification (draft-kasselman-oauth-dcr-trusted-issuer-token). Security properties include ephemeral, automatically rotated SVIDs, no secrets at rest, and every token event tied to a verifiable workload identity. This solves the "secret zero" problem -- the challenge of bootstrapping trust for a new agent instance without pre-distributing a shared secret.

Aembit's analysis frames the integration as a five-step flow: (1) service presents SPIFFE SVID, (2) platform verifies identity through SPIRE's trust bundle, (3) conditional access rules applied, (4) scoped OAuth token issued for short duration, (5) service accesses resources with token (never stored on disk). This pattern is directly applicable to requirement 9.4.1's mandate for unique cryptographic identity with no credential reuse.

The standards behind the MCP authorization profile are now mature enough to test directly. RFC 9728 requires a protected resource metadata document under `/.well-known/oauth-protected-resource`, with a `resource` value that exactly matches the protected resource identifier; if the returned value does not match, the client must not use that metadata. RFC 8707 adds the OAuth `resource` parameter so a client can request an access token for a specific protected resource and the authorization server can issue an audience-restricted token. In practice, an auditor should request separate tokens for two MCP or OpenAPI tool servers, confirm each token's audience is limited to the intended server, and verify that Tool B rejects a token minted for Tool A even when scopes look compatible.

The March 2026 OAuth SPIFFE Client Authentication draft closes another common gap: how an agent workload proves itself to the authorization server without a shared client secret. It profiles JWT-SVIDs, WIT-SVIDs, and X.509-SVIDs as OAuth client credentials, letting SPIFFE-backed agents authenticate to the authorization server with workload identity material instead of static secrets. This is especially useful for short-lived agents because identity can be issued by the workload platform, exchanged for scoped OAuth tokens, and rotated without distributing long-lived client credentials to agent code.

The November 2025 MCP authorization specification reinforces the same separation of identity and authorization. Authorization remains optional for MCP implementations, but protected HTTP MCP servers that support it act as OAuth resource servers: they advertise protected-resource metadata, require resource indicators so tokens are audience-bound to the intended MCP server, reject invalid or expired tokens, and must not accept or transit tokens issued for other resources. This gives auditors concrete checks for MCP tool servers: token audience validation, no token passthrough, short-lived tokens, HTTPS-only authorization endpoints, PKCE for authorization-code flows, and step-up scope challenges for higher-risk operations.

The IETF WIMSE Workload Proof Token draft adds an application-layer proof-of-possession pattern for workload calls that cannot rely only on mTLS. A WPT is a signed JWT carried in a `Workload-Proof-Token` header; it proves possession of the private key associated with the workload identity token, binds the proof to the HTTP target audience, uses very short lifetimes, and can include hashes of the workload identity token, OAuth access token, or transaction token. For agent systems, this is a useful bridge between 9.4.1 and 9.4.2: the call is not merely authenticated as an agent, but cryptographically tied to the exact request and delegated authorization context.

### Tamper-Evident Audit Tooling Matures

Beyond the AIVS draft specification, several open-source implementations of tamper-evident agent audit trails emerged in early 2026:

- **Clawprint** (cyntrisec; archived in April 2026 by its authors as a historical project, not a maintained product): Captures every trace from OpenClaw agent runs -- tool calls, outputs, lifecycle events -- and seals them in a SHA-256 hash chain ledger. Each trace's `hash_prev` points to the previous trace's `hash_self`. Storage uses SQLite with WAL mode and `synchronous=FULL` for durability, with Zstandard compression for artifact deduplication. Critically, Clawprint automatically redacts secrets (API keys, tokens, JWTs, AWS credentials, GitHub PATs) -- addressing the tension between audit completeness and credential exposure. Verification is a single command: `clawprint verify`.
- **CAP-SRP Protocol** (VeritasChain/AIMomentz): Records every AI generation, evaluation, and refusal in an append-only hash chain using `SHA-256(prev_hash | event_type | agent_id | timestamp_ms | JSON(payload))`. The protocol defines 22 distinct event types across 7 categories (content lifecycle, human interaction, learning, agent lifecycle, security, refusals, system). Each refusal generates a structured evidence pack with causal parent references enabling directed acyclic graph reconstruction of decision chains. Four public verification APIs enable external auditing without system access.
- **[AuditableLLM](https://doi.org/10.3390/electronics15010056)** (academic, _Electronics_, December 2025): A lightweight framework that decouples update execution from an audit-and-verification layer, recording each update as a hash-chain-backed, tamper-evident audit trail.

These implementations demonstrate that the tamper-evident audit 9.4.2 depends on is achievable with production-quality tooling, not just specification-level aspirations.

### Agent State Integrity: Memory Poisoning and Cryptographic Protection

Requirement 9.4.4 addresses a threat class that gained significant attention in 2025-2026: the integrity of agent state persisted between invocations. The OWASP Top 10 for Agentic Applications ranks memory poisoning as ASI06, recognizing that an attacker who can corrupt an agent's stored goals, context, partial results, or conversation history can cause the agent to exhibit misaligned behavior across future sessions -- with the attack and its execution temporally decoupled by days or weeks.

The MINJA attack (Dong et al., arXiv:2503.03704, "Memory Injection Attacks on LLM Agents via Query-Only Interaction," NeurIPS 2025) reported an average 98.2% success rate for injecting malicious records and 76.8% for eliciting the malicious reasoning, across three agents built on GPT-4 and GPT-4o in lab settings, using three techniques: bridging steps (intermediate reasoning that appears reasonable individually but leads toward malicious outcomes), indication prompts (crafted additions guiding agents to memorize malicious content), and progressive shortening (gradually removing explicit prompts while preserving malicious logic). A January 2026 follow-up (arXiv:2601.05504, "Memory Poisoning Attack and Defense on Memory Based LLM-Agents") tested GPT-4o-mini, Gemini 2.0 Flash, and Llama 3.1 8B on clinical data and found that pre-existing legitimate memories dramatically reduced attack success, so the headline rates are best-case lab results. Separately, [delayed tool invocation attacks against Google Gemini's memory feature](https://embracethered.com/blog/posts/2025/gemini-memory-persistence-prompt-injection/) (Embrace The Red, February 2025) showed that conditional instructions planted in processed documents activate when victims naturally use trigger words, bypassing guardrails to permanently install false memories. AgentPoison (arXiv:2407.12784, 2024) and MemoryGraft (arXiv:2512.16962, December 2025) extend the same playbook to backdoor-triggered memory and knowledge-base poisoning and to poisoned experience retrieval that causes persistent behavioral drift.

Cryptographic integrity protection for agent state requires several layers. At the entry level, every memory write should include a SHA-256 checksum computed over the content, user identity, and a secret key -- the approach demonstrated in the OWASP AI Agent Security Cheat Sheet's `SecureAgentMemory` class. More robust implementations use cryptographic MACs (HMAC-SHA256) or digital signatures to bind each state entry to the agent's identity and a timestamp, ensuring that tampering is detectable even if the storage layer is compromised. Metadata provenance -- recording the source (user, system, or external), creating agent identity, session context, and initial trust score for every entry -- enables the runtime to apply trust-weighted retrieval that demotes low-provenance data.

The OWASP Agent Memory Guard project (incubator, targeting v1.0.0 by Q4 2026) provides a runtime defense layer for LangChain, LlamaIndex, and CrewAI agents. It enforces declarative YAML security policies on memory read/write operations, validates integrity using SHA-256 cryptographic baselines, detects injection attempts and sensitive data leakage, and supports snapshots with rollback to known-good states. This addresses the integrity-protection expectation in 9.4.4 -- if a memory entry fails integrity verification, the runtime can quarantine it and optionally roll back to the last verified snapshot rather than proceeding with potentially poisoned state.

A complementary library, **mguard** (MIT, published on npm; "six layers of defense in three lines of code," zero dependencies), targets MINJA, AgentPoison, and MemoryGraft directly. It Ed25519-signs every memory entry at creation and quarantines tampered entries on read, layers a Beta-Binomial Bayesian trust score with asymmetric updates that favor clean writes, ships six attack-pattern detectors (bridging-redirect, instruction-injection, exfiltration-setup, conditional-trigger, progressive-shortening, trust-manipulation), adds EWMA write-frequency anomaly detection for burst-write attacks, applies trust-gated retrieval so low-trust entries are filtered at read time, and keeps a hash-chained, tamper-evident audit of memory operations. It wraps Mem0 (`shieldMem0()`), LangChain (`shieldLangChain()`), and custom stores (`shield()`). Where Agent Memory Guard leans on SHA-256 baselines and YAML policy, mguard leans on per-entry signatures and probabilistic trust -- the two are usefully combined.

### Audit Log Context: What "Sufficient" Means in Practice

Reconstructing who acted, why they were authorized, what they did, and what happened depends on audit records rich enough to support non-repudiation (requirement 9.4.2). As of early 2026, industry guidance has converged on a minimum field set for agent audit records:

- **Actor identity:** Agent ID (cryptographic, not display name), with the full delegation chain back to the initiating human principal
- **User context:** Initiating user identifier, tenant, session ID, and the delegation scope defining what the agent is authorized to do on the user's behalf
- **Authorization decision:** The policy name, version, and evaluation result (allow/deny) that authorized or blocked the action -- without the policy version, post-incident reviewers cannot determine whether an action was legitimate under the rules in effect at the time
- **Tool parameters:** The specific tool invoked, operation type, and parameters passed (with sensitive values redacted -- logging `{"customer_id": "<redacted>"}` rather than raw PII)
- **Approval context:** Whether human approval was required and obtained, the approver identity, and the approval timestamp
- **Outcome:** Action result (success, failure, partial), any error codes, and downstream effects

Distributed tracing (OpenTelemetry trace IDs, W3C Trace Context) provides the correlation mechanism, with each agent action creating a child span linked to its parent. The OpenInference trace format, designed specifically for AI workloads, extends standard tracing with fields for prompt content, model decisions, and tool call results. For MCP environments, Tetrate's audit logging guidance recommends capturing every tool invocation with parameters, authorization checks, and data access patterns as first-class log events rather than debug traces.

OpenTelemetry's GenAI semantic conventions now define development-status spans for agent creation, agent invocation, workflows, and tool execution, with fields such as `gen_ai.agent.id`, `gen_ai.agent.version`, `gen_ai.conversation.id`, `gen_ai.input.messages`, `gen_ai.output.messages`, and `gen_ai.tool.definitions`. These conventions are useful for consistent telemetry naming, but they are not a substitute for evidence: the span identifiers and tool-call fields still need to be bound into signed or hash-chained audit records before they can support non-repudiation.

The harder challenge is enforcement: most agent frameworks do not emit structured logs with all required fields by default. Custom instrumentation -- either through middleware hooks or framework-specific plugins -- remains necessary. Incidents such as the March 2026 Meta case show why this matters, because reconstructing which agent acted, under whose delegation, and on what authorization decision depends on those fields being recorded.

The authorization-decision field got a standardization boost in early 2026 when the OpenID Foundation finalized AuthZEN (Authorization API 1.0), a vendor-neutral JSON API between policy enforcement points and policy decision points. For agent architectures, externalizing authorization through an AuthZEN-style PDP has a direct benefit for 9.4.2 non-repudiation: every tool-call authorization becomes an explicit, loggable request/response pair (subject, action, resource, context, decision) rather than an implicit branch buried in application code. Auditors can then verify that the decision recorded in the audit chain matches what the PDP actually returned, and policy versions can be tracked at the PDP rather than reverse-engineered from agent code. Cerbos, Axiomatics, and other vendors passed the working group's [May 2024 interoperability testing](https://openid.net/authorization-interop-results/), well before 1.0 (Cerbos [documents](https://docs.cerbos.dev/cerbos/latest/api/) a partial implementation of the API), and gateway implementations are emerging that apply the same PEP/PDP pattern to MCP tool calls.

### CVE-2026-32211: MCP Authentication Absence as Systemic Risk

On April 2, 2026, Microsoft published [CVE-2026-32211](https://msrc.microsoft.com/update-guide/vulnerability/CVE-2026-32211) (CVSS 9.1 per Microsoft's CNA score; NVD's own score is 7.5): missing authentication for a critical function in Azure MCP Server (CWE-306) let an unauthorized attacker disclose information over a network. Microsoft lists it as a cloud-service issue that required no customer action. The structural point stands: the MCP specification makes authorization optional, and implementations that skip it ship critical gaps. This is one concrete example of how the MCP protocol's optional-auth design leaves gaps in agent infrastructure, reinforcing why requirement 9.4.1's mandate for cryptographic identity must extend to every component in the agent stack, including tool servers.

Simultaneously, CVE-2026-32173 (CVSS 8.6 per Microsoft; NVD scores it 7.5) revealed improper authentication in the Azure SRE Agent, allowing unauthorized information disclosure. Two agent-identity CVEs from the same vendor in the same month illustrate the systemic nature of the problem.

The pattern continued in May 2026 with CVE-2026-42856 in the `network-ai` npm package. GitLab's advisory describes an MCP HTTP transport that accepted unauthenticated JSON-RPC `tools/call` requests, bound by default to `0.0.0.0`, and dispatched them straight to the orchestrator tool registry. The fixed version is 5.1.3. For C9.4 reviewers, this is a useful regression test: every MCP tool endpoint should reject unauthenticated calls before tool enumeration, and audit evidence should show the authenticated agent identity, caller, chain ID, authorization decision, and exact tool operation for every accepted request.

### May 2026 MCP Identity-Boundary CVEs

By May 2026, the MCP vulnerability pattern had shifted from simple missing authentication toward broken identity boundaries around "local" transports, shared bearer tokens, middleware routing, and tool-handler parameters. These cases are useful for C9.4 because they show why agent identity has to be checked before transport, middleware, and tool execution decisions, not only inside the final tool handler.

- **CVE-2026-44694 and CVE-2026-39974 (n8n-MCP):** authenticated SSRF in multi-tenant HTTP mode let a caller with a valid token steer requests through webhook trigger tools, the configured `N8N_API_URL`, or per-request `x-n8n-url` headers. The audit concern is not just "who had a token"; the receipt needs the tenant, token subject, requested URL, resolved endpoint, allowlist decision, and chain ID before the outbound request occurs.
- **CVE-2026-35568 (MCP Java SDK) and CVE-2026-35577 (Apollo MCP Server):** DNS rebinding and Host-header validation gaps let a malicious browser context reach local or network-private MCP servers and make calls as though it were the locally connected agent. Reviewers should test HTTP MCP servers with hostile `Host` and `Origin` values, DNS rebinding harnesses, and browser-driven requests to loopback/private addresses. Passing stdio tests is not enough for StreamableHTTP deployments.
- **CVE-2026-33980 (Azure Data Explorer MCP Server):** KQL injection in schema and sampling tools allowed attacker-controlled table names to reach query construction. This is a reminder that a valid agent identity does not make parameters safe: tool receipts should include canonicalized parameter hashes, policy decisions tied to permitted tables or datasets, and the exact query template or query hash used for execution.

The practical verification rule is to capture identity and authorization evidence at every boundary where trust can change: browser to local server, client to MCP HTTP transport, middleware to upstream service, tool handler to datastore, and orchestrator to downstream agent. A chain-bound audit record that starts only after the final tool handler accepts the call will miss the classes of failure these CVEs exposed.

### Claw Chain: Identity Spoofing via Client-Controlled Metadata

In May 2026, Cyera researcher Vladimir Tokarev disclosed four chainable OpenClaw vulnerabilities collectively dubbed "Claw Chain," all fixed in OpenClaw 2026.4.22. The identity lesson sits in CVE-2026-44118 (CVSS 7.8): OpenClaw's MCP loopback endpoint determined owner status from a client-supplied `x-openclaw-sender-is-owner` HTTP header rather than from the authenticated session. Any non-owner loopback client holding a valid bearer token could assert the header and receive owner-gated functionality -- gateway configuration, cron scheduling, and execution environment management. The fix is instructive for 9.4.1 reviewers: the patched runtime issues separate owner and non-owner bearer tokens and derives the ownership claim exclusively from which token authenticated the request, never from caller-controlled metadata.

The companion CVEs complete an attack chain that an auditor should treat as a template: CVE-2026-44113 (TOCTOU sandbox read escape) and CVE-2026-44115 (heredoc shell-expansion allowlist bypass) harvest credentials and sensitive files, CVE-2026-44118 escalates to owner-level control, and CVE-2026-44112 (TOCTOU write escape, CVSS 9.6) plants persistence. Cyera's framing is the audit-relevant point: each step looks like normal agent behavior to traditional controls, because the adversary is using the agent's own privileges as their hands inside the environment. Only chain-bound audit records that capture the authenticated identity behind every privileged operation (9.4.2) make this kind of living-off-the-agent attack reconstructable. The episode generalizes a rule already visible in CVE-2026-44694's `x-n8n-url` header abuse: any identity or routing decision derived from client-controllable request metadata is an impersonation primitive waiting to be used.

### SPIFFE Instance-Level Identity: The Replica Granularity Problem

As of April 2026, a practical gap has emerged in applying SPIFFE to agent workloads. Standard Kubernetes/Istio deployments anchor SPIFFE identities to service accounts, meaning all replicas of a given agent deployment receive identical credentials (e.g., `spiffe://acme.com/ns/trading/sa/trading-agent-sa`). This works for stateless microservices but breaks down for agents, which develop unique contexts through interactions, RAG data, and conversation history. Each instance behaves differently, yet security policies cannot distinguish between them -- an unauthorized 3 AM trading pattern becomes impossible to attribute to a specific agent instance.

SPIFFE's specification does permit instance-level granularity (e.g., `spiffe://acme.com/ns/trading/sa/trading-agent-sa/instance/001`), but this creates cascading authorization challenges: policies must now handle dynamically generated identities, identity-to-permission mappings cannot be pre-configured, and the identity lifecycle management overhead scales linearly with instance count. Organizations deploying SPIFFE for agent identity should plan for instance-level SVIDs from the outset rather than retrofitting replica-level identities.

### Google Cloud Agent Identity: Hyperscaler-Native SPIFFE for Agents

Google Cloud's Agent Identity (documentation last updated September 24, 2026; the auth manager pages carry no Preview label) is a hyperscaler primitive that issues per-agent SPIFFE identities natively. Each deployed agent receives a unique SPIFFE ID of the form `spiffe://agents.global.org-NUMBER.system.id.goog/resources/aiplatform/.../reasoningEngines/AGENT` plus an auto-provisioned X.509 certificate valid for 24 hours and rotated automatically. Three properties matter for C9.4 verification. First, the SPIFFE path encodes the specific agent resource, not a shared service account -- addressing the replica-granularity problem at the platform layer. Second, Google Cloud access tokens are cryptographically bound to the agent's X.509 certificate, with a managed Context-Aware Access policy enforcing demonstrable proof-of-possession (DPoP) and mTLS at the Agent Gateway -- so a stolen token cannot be replayed without the agent's private key, directly mitigating the bearer-token exfiltration pattern seen in ClawBleed. Third, Cloud Audit Logs attribute events to the agent's SPIFFE ID and distinguish the agent acting as itself from the agent acting on behalf of an end user, which is precisely the delegation context that non-repudiation (9.4.2) requires. Google's documentation lists Gemini Enterprise Agent Platform Runtime, Gemini Enterprise, and Cloud Run as supported, so coverage is limited to Google-hosted runtimes, but the design is a useful benchmark: when evaluating any platform against 9.4.1 and 9.4.3, ask whether it offers per-agent identity, sender-constrained tokens, sub-day automatic rotation, and identity-attributed audit -- this stack shows all four are deliverable today. HashiCorp's Vault has moved the same direction: Vault Enterprise 1.21 added native SPIFFE authentication, and Vault Enterprise 2.0 adds a SPIFFE secrets engine that issues JWT-SVIDs directly, letting agents exchange workload identity for scoped secrets without static credentials.

### Alibaba Open Agent Auth: Enterprise Authorization Framework

Alibaba's Open Agent Auth (Apache 2.0, public beta v0.1.0-beta.1 as of April 2026) implements a zero-trust, layered authorization architecture for AI agent operations. This ensures every agent operation traces back to explicit user consent through verifiable cryptographic linkage -- not just session cookies or bearer tokens.

Key capabilities include virtual workload patterns implementing WIMSE standards with request-level isolation and automatic credential cleanup, fine-grained authorization via OPA/RAM/ACL policy engines with hot-reload (no service restart), and semantic audit trails using W3C Verifiable Credentials to document complete operational context. The framework ships with Spring Boot 3.x autoconfiguration and an MCP adapter. While still in beta (targeting 1.0.0 for production readiness), it is an open-source implementation of the IETF WIMSE specification for agent workloads.

### CVE-2026-25253 (ClawBleed): Agent Token Exfiltration via WebSocket Hijacking

CVE-2026-25253, dubbed "ClawBleed" (CVSS 8.8), disclosed in February 2026 and confirmed as actively exploited in the wild, demonstrated a particularly insidious agent identity attack: OpenClaw's Control UI automatically trusted URL-supplied `gatewayUrl` query parameters and established WebSocket connections that transmitted the user's stored authentication token without origin verification. An attacker who crafted a malicious URL could steal the victim's agent authentication token in a single click -- the token was transmitted to an attacker-controlled WebSocket endpoint in milliseconds. Because OpenClaw operates with full system access (file operations, shell command execution), compromising an operator's authentication token granted complete control over the victim's machine, including credential theft from the OpenClaw Vault (AWS keys, database passwords), infrastructure destruction, and CI/CD pipeline manipulation. ClawBleed illustrates a pattern distinct from the other OpenClaw vulnerabilities: rather than exploiting supply chain weaknesses (malicious skills) or missing authentication (API endpoints), it weaponized the agent's own identity mechanism -- the authentication token became the attack vector. Requirement 9.4.1's insistence on cryptographic identity bound to specific workloads (not transferable bearer tokens) would have limited the blast radius significantly.

### ZeroID: Open-Source Identity Platform for Autonomous Agents

ZeroID (Apache 2.0, by Highflame, released April 2026) is a purpose-built identity and credentialing platform for autonomous AI agents and multi-agent systems. Its core innovation is RFC 8693 token exchange creating verifiable delegation chains -- when an orchestrator agent spawns sub-agents, each receives a token that carries the sub-agent identity, orchestrator identity, and original authorizing principal. Scope attenuates automatically at each delegation hop, so sub-agents cannot receive permissions the orchestrator does not already hold. Revoking any token in a delegation chain immediately invalidates all downstream tokens.

Key capabilities relevant to requirements 9.4.1 and 9.4.3:

- OpenID Shared Signals Framework (SSF) and Continuous Access Evaluation Profile (CAEP) integration for real-time revocation without polling delays
- Local JWT verification against cached JWKS endpoints for low-latency scenarios
- SDKs for Python, TypeScript, and Rust, with framework integrations for LangGraph, CrewAI, and Strands
- Containerized deployment backed by PostgreSQL, with a hosted option at auth.highflame.ai

ZeroID complements SPIFFE-based approaches: where SPIFFE anchors workload identity at the infrastructure level, ZeroID handles the application-layer delegation chain and scope attenuation that agents require for multi-hop task execution.

### Asqav: Quantum-Resistant Agent Audit Trail SDK

Asqav (MIT license, Python SDK, released April 2026) takes a distinctive approach to agent audit trails by using ML-DSA-65 (FIPS 204 standardized) post-quantum digital signatures rather than the Ed25519 signatures common in other implementations. Each agent action receives a quantum-resistant cryptographic signature with RFC 3161 timestamps, and entries link into a hash chain where tampering or omission breaks verification.

Practical features for requirement 9.4.2:

- Framework support for LangChain, CrewAI, LiteLLM, Haystack, and OpenAI Agents SDK
- Simple integration via decorator (`@asqav.sign`) or context manager (`asqav.session()`)
- Policy enforcement at the action level -- block patterns like `data:delete:*`
- Multi-party signing using an m-of-n threshold scheme for high-stakes actions requiring multiple approvals
- Offline mode with local signing and later sync for air-gapped or intermittently connected environments

Asqav's maintainers chose post-quantum signatures by default, addressing the longer-term concern that Ed25519-signed audit records may become verifiably insecure as quantum computing capabilities mature. For organizations with multi-decade record retention requirements (healthcare, financial services), quantum-resistant signing future-proofs the audit trail.

### IETF Agent Audit Trail (AAT) Draft Specification

A third IETF Internet-Draft relevant to agent audit emerged in March 2026: draft-sharif-agent-audit-trail-00 by Raza Sharif (CyberSecAI Ltd) defines a standardized JSON-based logging format specifically for autonomous AI agent systems. Where the AIVS draft (draft-stone-aivs-00) focuses on session-level cryptographic proof bundles, AAT targets operation-level structured logging suitable for SIEM ingestion and regulatory compliance.

Mandatory record fields include: `record_id` (UUIDv4), `timestamp` (RFC 3339), `agent_id` (URI), `agent_version`, `session_id`, `action_type`, `action_detail`, `outcome`, `trust_level`, `parent_record_id`, and `prev_hash` (SHA-256 via RFC 8785 JSON Canonicalization Scheme). Optional ECDSA P-256 signatures provide non-repudiation. The specification defines seven action types: `tool_call`, `tool_response`, `decision`, `delegation`, `escalation`, `error`, and `lifecycle`.

Two design decisions distinguish AAT from other approaches. First, privacy-by-design: input/output data is replaced with hashes rather than stored in plaintext, and GDPR right-to-erasure requests are handled via tombstone records that preserve chain integrity. Second, explicit regulatory mappings to EU AI Act Articles 12-14, SOC 2 Trust Services Criteria, ISO/IEC 42001, and PCI DSS v4.0.1 -- making compliance mapping concrete rather than aspirational. Export formats include JSONL (primary), Syslog (RFC 5424), and CSV.

The verifier detail is useful for C9.4 audits even if AAT itself remains a draft. A conformant validator checks that mandatory fields are present, recomputes `prev_hash` values against canonical JSON records, confirms timestamps are monotonically ordered, and verifies session structure from genesis record to close record. For high-throughput agents, the draft allows asynchronous or batched hash computation only when event-time ordering is preserved, which gives reviewers a practical way to test whether batching has weakened the chain-of-custody guarantee.

AAT, AIVS, and the LangChain ComplianceCallbackHandler RFC represent three complementary approaches to the same underlying need: AAT for structured log ingestion, AIVS for portable cryptographic proof bundles, and the LangChain RFC for framework-native integration. Organizations may end up using more than one depending on their compliance requirements and technology stack.

### SCITT-Based Permit and Closure Receipts

As of July 2026, [RFC 9943](https://www.rfc-editor.org/rfc/rfc9943.html) is the IETF Proposed Standard substrate for signed statements and transparency-service receipts. The May 2026 individual draft *A SCITT Profile for Pre-Execution AI Action Authorization Records* applies that architecture to a particularly useful negative-test pattern for requirement 9.4.2. Before dispatch, the policy issuer creates a COSE-signed Permit containing a hash of the authorized request. After dispatch, it creates a separately signed Closure Record containing the dispatched-request digest and provider-response digest. A verifier must reject the evidence bundle when the closure's request digest differs from the permit's binding hash; the draft calls this the canonical "approved-but-modified" tampering signature.

The profile records permits and closures in a per-scope linked hash chain with signed checkpoints. This makes omission and reordering detectable, but verification cost grows with the distance from the last checkpoint, so checkpoint cadence becomes an auditable operational parameter. It is still an individual Internet-Draft, not an adopted standard. Its strongest immediate value is as a concrete test oracle: alter a tool argument after approval, omit the closure record, break `prev_hash`, or substitute a response digest and confirm that offline verification returns a stable integrity failure rather than a valid-looking partial trace.

### LiteLLM Supply Chain Attack: Credential Theft from AI Infrastructure

On March 24, 2026, threat actor TeamPCP published backdoored versions of the LiteLLM Python package (versions 1.82.7 and 1.82.8) after stealing PyPI credentials via a compromised Trivy GitHub Action in LiteLLM's CI/CD pipeline. LiteLLM averages 3.4 million downloads per day. The packages were live for approximately 40 minutes before PyPI quarantined them, but the attack chain was devastating:

- Version 1.82.7 embedded a base64-encoded payload inside `litellm/proxy/proxy_server.py`, executing on any import of `litellm.proxy` -- the standard import path for LiteLLM's proxy server mode.
- Version 1.82.8 added a `.pth` file to `site-packages/`, which fires on every Python interpreter startup with no import required -- including pip, `python -c`, or IDE language servers.
- The payload ran a three-stage attack: harvest credentials (SSH keys, cloud tokens, Kubernetes secrets, crypto wallets, `.env` files), attempt lateral movement across Kubernetes clusters by deploying privileged pods to every node, and install a persistent systemd backdoor.

For agent identity, this attack demonstrates that AI development infrastructure is now a first-class supply chain target. Agents built on compromised libraries inherit the compromise -- their credentials, API keys, and cloud tokens are exfiltrated before the agent even starts operating. Requirement 9.4.1's mandate for unique cryptographic identity is necessary but insufficient without supply chain integrity for the agent's own runtime dependencies (see also C06 Supply Chain requirements).

This data directly supports requirement 9.4.3's mandate for credential rotation and rapid revocation -- long-lived, broadly scoped agent credentials are precisely the kind of NHI that attackers exploit at scale.

### Oktsec: Open-Source Agent Communication Security

Oktsec (Apache 2.0, Go) provides a runtime security gateway for agent-to-agent communication, implementing a 10-stage security pipeline that intercepts, validates, and logs every tool call and inter-agent message. Key capabilities relevant to requirements 9.4.1 and 9.4.2:

- **Ed25519 cryptographic signing** of all messages: each agent receives a keypair, and messages must include a signature covering sender, recipient, content, and timestamp. Signature verification runs at approximately 120 microseconds per message. When `require_signature: true`, unsigned messages are rejected immediately.
- **Hash-chained audit trail** where each log entry links to the previous via Ed25519 signatures, enabling offline tamper verification.
- **268 content detection rules** (the repository's current count) covering categories such as credential leaks, prompt injection, MCP attacks, and container escapes, with policy decision logging recording ACL verdicts, rule matches, and sender verification status per message.
- Single statically compiled Go binary with zero external dependencies, SQLite storage with WAL mode, and no cloud requirement. Supports MCP (official Go SDK), HTTP/JSON-RPC 2.0, and WebSocket transports.

Oktsec represents a practical open-source implementation of the agent-identity and chain-binding requirements in 9.4.1 and 9.4.2, deployable as a sidecar or gateway in existing agent architectures.

### Cryptographic Receipts for Agent Actions: AgentMint and ArkForge

Two complementary open-source projects emerged in early 2026 for generating verifiable cryptographic proof of agent actions:

- **AgentMint** (a Rust sidecar) issues short-lived, single-use Ed25519-signed tokens proving that a human approved a specific agent action, and returns an Ed25519-signed receipt.
- **ArkForge** acts as a certifying proxy: the caller routes requests through ArkForge, which signs the full request+response bundle with an Ed25519 key, timestamps it via RFC 3161, and anchors it in Sigstore Rekor -- an immutable, publicly auditable log.

These implementations address the gap between 9.4.2's requirement for signed, timestamped action records and the reality that most agent frameworks emit no cryptographic proof by default. They are lightweight enough to integrate as middleware.

### RSAC 2026: Five Frameworks, Three Gaps

RSA Conference 2026 (March) saw five major vendors ship agent identity frameworks: CrowdStrike (AI Detection and Response with Shadow SaaS and AI Agent Discovery), Cisco (Duo Agentic Identity with MCP gateway enforcement), Palo Alto Networks (agent visibility dashboards), Microsoft (Entra Agent ID for Agent 365), and Cato CTRL (agent discovery and authentication). The density of announcements signals that agent identity has graduated from niche concern to mainstream security category.

CrowdStrike's CEO disclosed two unnamed Fortune 50 incidents at the conference: a CEO's AI agent rewrote the company's security policy to remove a restriction, and a 100-agent Slack deployment in which one agent committed code that the team found only afterward. VentureBeat reported that every identity check passed in the first case. Commentators then named gaps that identity frameworks leave open, and they do not agree on the list: VentureBeat named agent self-modification, agent-to-agent delegation, and ghost agents with live credentials, while a vendor analysis (Aguardic) named the three below, so treat these as one framing rather than a settled list:

1. **Tool-call authorization layer:** OAuth confirms agent identity but does not constrain actions. An agent authenticated to a Jira instance can create tickets, close tickets, modify project settings, and delete boards -- identity alone cannot evaluate whether specific parameter and intent-to-action combinations are appropriate.
2. **Permission drift management:** Agent capabilities expand faster than security review cycles. The frameworks provide point-in-time visibility but lack continuous monitoring of how privileges accumulate over time.
3. **Audit trail evidence:** Identity systems cannot reconstruct full decision chains. The Slack swarm incident -- where 100+ agents collaborated and Agent 12 committed code without human approval -- exposed the inability to produce an immutable record of the original prompt, each agent's proposed action, and each delegation decision.

These gaps reinforce why cryptographic identity (9.4.1) is necessary but not sufficient on its own: action-level authorization and continuous permission governance are a separate control set in C9.5 (Agent Authorization, Delegation, and Continuous Enforcement), and chain-bound audit evidence (9.4.2) is a separate control again.

### Cisco Duo Agentic Identity: MCP Gateway Enforcement

Cisco's Duo Agentic Identity (announced at RSAC 2026) takes a distinctive approach by placing an MCP gateway between agents and the tools they access. Customers register agents in Duo IAM and map them to accountable human owners. Every tool call routes through the gateway, which evaluates requests against Duo's fine-grained authorization engine before permitting or blocking the action. Policies map specific agent identities and groups to specific tool calls with granular control over scope, conditions, and permitted operations. Cisco Identity Intelligence extends discovery to agentic and non-human identities, providing visibility into existing AI usage across the enterprise. Combined with Cisco's Secure Access SSE, the architecture treats agent traffic as first-class network citizens subject to the same Zero Trust policies as human users.

### IETF Standardization Updates: AIMS -03, WIMSE Workload Credentials -02, and Dual Identity

Two July 2026 draft revisions make identity granularity and proof-of-possession more concrete for implementers:

**[draft-klrc-aiagent-auth-03](https://datatracker.ietf.org/doc/draft-klrc-aiagent-auth/) (July 6, 2026):** The current AIMS draft requires every agent to have a unique identifier, exactly one WIMSE identifier for its workload identity, and a primary credential cryptographically bound to that identifier. It treats static API keys as an anti-pattern because bearer keys neither prove control of an agent-specific key nor provide a reliable agent identity. This sharpens the 9.4.1 test: a valid certificate or token is insufficient if several live agent instances still resolve to the same downstream principal.

**[draft-ietf-wimse-workload-creds-02](https://www.ietf.org/archive/id/draft-ietf-wimse-workload-creds-02.html) (July 2, 2026):** The WIMSE credential profile requires each workload to know its own identifier and requires an explicit mapping between the external handle used to reach a workload and that workload identifier. For agent deployments, auditors should verify both sides of that mapping. A downstream service that validates only a trust domain, service alias, Kubernetes service account, or ingress name may authenticate the platform while still collapsing multiple agent instances into one principal.

**draft-ni-wimse-ai-agent-identity-02 (February 28, 2026):** This companion draft introduces "dual-identity credentials" that cryptographically bind an agent's identity to its owner's identity, addressing accountability gaps in cross-organizational interactions. It defines three issuance models: (1) agent-mediated, where the owner pre-signs requests locally with support for hardware-based binding; (2) owner-mediated, where the owner acts as supervisory gateway inspecting all requests; and (3) server-mediated, where the server orchestrates real-time confirmation via challenge-response with the owner. This framework fills a gap the original AIMS draft left open -- how to maintain the chain of accountability from agent back to human across trust boundaries.

### Agent Identity Protocol Draft: Capability-Centric Delegation

The April 2026 Agent Identity Protocol (AIP) draft takes a more opinionated path than AIMS or WIMSE. Instead of composing existing workload identity and OAuth patterns, it defines a decentralized identity layer using `did:aip`, Ed25519-backed agent identities, capability manifests, credential tokens, principal tokens, revocation objects, and approval envelopes for multi-step workflows. Its consent ceremony is especially relevant to C9.4: before a principal wallet signs a grant, it must display the agent name, model provider and model ID, purpose, deployer identity, requested capabilities, delegation lifetime, and extra friction for destructive operations.

The useful verification takeaway is not that AIP should be adopted as-is. It is still an Internet-Draft and overlaps with AIMS, WIMSE, AIVS, and AAT. The takeaway is that standards work is converging on the same evidence shape: agent identity, human or organizational sponsor, narrowly scoped capabilities, signed delegation, revocation status, and verifiable action records. Auditors should ask whether the deployment can produce that chain of evidence even if it uses Entra, SPIFFE, OAuth, Duo, or a custom gateway rather than AIP itself.

### Microsoft Entra Conditional Access: Three Agent Access Patterns

Microsoft's Entra documentation (the Conditional Access page is dated July 2026) gives a practical implementation model for agent access governance. Conditional Access now distinguishes three patterns: an agent acting on behalf of a signed-in user, an agent using its own application identity, and an agent operating through an agent user account. The verification detail that matters for C9.4 is token subject and audience: an on-behalf-of flow issues a resource-specific token for the user, an application-only flow issues the token to the agent identity, and an agent user account flow evaluates policy against the linked non-human user account.

Two limitations are worth testing directly. First, Conditional Access only protects resources secured by Entra ID; API keys and unmanaged bearer tokens bypass the policy engine entirely. Second, token acquisition is the enforcement point, so stale long-lived tokens, cached downstream credentials, and custom MCP servers that are not registered as protected resources can create gaps. A good audit should review sign-in logs for `agentType` (see [Entra Agent ID logs](https://learn.microsoft.com/en-us/entra/agent-id/identity-professional/sign-in-audit-logs-agents)), confirm every MCP/OpenAPI tool server has an enterprise application and exposed permissions, and test that high-risk agent identities are blocked or quarantined when risk signals change.

### MCP Middleware SSRF: Identity Checks Below the Tool Layer

The `mcp-atlassian` SSRF (CVE-2026-27826, fixed in 0.17.0; RAXE advisory March 2026) is a useful reminder that agent identity checks can fail below the tool implementation itself. In HTTP transport mode, middleware accepted attacker-controlled Jira or Confluence URL headers, constructed API clients from those headers, and triggered outbound requests before tool-level authorization logic could help. The confirmed impacts included internal network reconnaissance, cloud metadata credential theft, and prompt injection through attacker-controlled responses returned as apparently legitimate Atlassian data.

For C9.4, the lesson is that action receipts need to include middleware decisions, not just final tool calls. If the audit chain records only "agent called Jira search," it may miss the fact that the middleware silently redirected the call to an attacker-controlled endpoint. Verification should therefore include transport mode, inbound header validation, target URL allowlists, private-network egress blocking, token audience checks, and signed receipts that capture the resolved endpoint actually contacted.

### McHire Incident: Default Credentials on AI Hiring Platform

The McHire exposure (found by researchers Ian Carroll and Sam Curry in June 2025 and detailed publicly in July 2025) provides a stark counterpoint to the cryptographic identity requirements in 9.4.1. Researchers discovered that McDonald's AI-powered hiring chatbot "Olivia," built by Paradox.ai and processing applications across 44,000+ locations, was protected by the default username "123456" and password "123456." This gave administrator access to live hiring data. An IDOR vulnerability then allowed sequential enumeration of up to 64 million applicant records including names, contact information, and interview transcripts. The root cause was not a protocol failure but the complete absence of identity rigor for an AI system with access to massive personal data stores. This reinforces that cryptographic identity (requirement 9.4.1) must be treated as a foundational requirement -- regardless of its Level 2 placement -- because the failure mode of weak identity is catastrophic data exposure at scale.

### Qualys ETM: Agent Compromise to Domain-Wide Identity Exploitation

A Qualys Enterprise TruRisk Management blog walkthrough (April 13, 2026) shows how an agent vulnerability can be correlated with identity weaknesses into a path toward enterprise-wide compromise. It is a vendor product demonstration of an investigation, not an independently reported incident. An unauthorized OpenClaw agent on a Windows Server 2025 EC2 instance was detected running a vulnerable OpenClaw package (CVE-2026-25253, CVSS 8.8). Qualys ETM correlated the agent-level vulnerability with two identity misconfigurations: accounts with SID History tied to non-existing domains (enabling SID-History Injection and impersonation of privileged identities) and accounts lacking Kerberos pre-authentication requirements (exposing AS-REP Roasting for credential compromise). The combination transformed a single agent endpoint vulnerability into a viable path to Domain Admin and Domain Controllers. Without identity telemetry correlation, the OpenClaw finding would have appeared as an isolated software vulnerability -- with it, the potential blast radius extended to the domain. This illustrates why agent identity (9.4.1) cannot be evaluated in isolation from the broader identity infrastructure.

### EU AI Act Article 12: Framework-Level Compliance Tooling

With the EU AI Act's high-risk logging obligations now set for December 2, 2027 (deferred from August 2, 2026 by the Digital Omnibus on AI), framework-level compliance tooling is emerging. The deferral does not pause everything: the AI Office's GPAI enforcement powers -- fines up to 3% of global annual turnover or EUR 15 million, information requests, and model recalls -- activate on August 2, 2026, and the European Commission's AI Act Service Desk has confirmed that AI agents fall under the existing AI-system and GPAI-model definitions rather than a separate category. Deployers of high-risk systems also face Article 26(6)'s six-month minimum log retention, which makes tamper-evident storage a retention obligation, not just a forensic nicety. LangChain's RFC for a ComplianceCallbackHandler (GitHub issue #35691) proposes native tamper-evident audit trail support for regulated industries. The `langchain-nobulex` middleware already provides hash-chained audit logs targeting EU AI Act (Regulation 2024/1689) requirements. As of April 2026, Article 12 specifically requires that high-risk AI systems support automatic logging of events throughout their lifecycle with logs that regulators can inspect -- making tamper-evident audit (supporting 9.4.2 non-repudiation) a legal obligation, not just a best practice, for agents deployed in EU-regulated contexts.

| **9.4.1** | **Verify that** each agent instance has a unique cryptographic identity and authenticates as a first-class principal to downstream systems. | 2 | **Agent impersonation and confused deputy.** Without unique identity, agents may share credentials or reuse end-user tokens, making it impossible to distinguish agent actions from user actions or one agent from another. Start a replacement instance, confirm it receives a distinct principal, and verify that the retired instance's credential and a cloned credential are rejected. | **9.4.2** | **Verify that** agent-initiated actions are cryptographically bound to each step of the execution chain for non-repudiation. | 2 | **Trace spoofing, orphaned tool calls, and broken chain-of-custody.** A plain trace ID proves correlation, not authenticity: a malicious client, compromised tool server, or rogue sub-agent can inject or replay a `traceparent`/chain identifier unless each action record is bound to the previous step and to the agent identity. Missing chain binding lets attackers make a destructive tool call look like an unrelated event, drop denied policy checks from the record, or sever delegation evidence between an orchestrator and downstream agents. FastGPT's April 2026 unauthenticated HTTP tool endpoint and MCP SSRF CVEs illustrate the operational risk: agent platforms can trigger network actions across trust boundaries, so defenders need cryptographic evidence of which run, policy decision, and principal caused each call. | Verify that every external action, tool call, delegation, and inter-agent message carries the current chain ID plus a parent span/record reference. | **9.4.4** | **Verify that** agent state persisted between invocations is integrity-protected. | 3 | **Memory poisoning and persisted-state tampering (OWASP Agentic ASI06).** An attacker who corrupts an agent's stored goals, context, partial results, or conversation history can induce misaligned behavior in future sessions, with the attack and its execution temporally decoupled by days or weeks. MINJA (memory injection via query-only interaction) reported 98.2% average injection and 76.8% attack success against GPT-4 and GPT-4o based agents in lab settings (arXiv:2503.03704), though a January 2026 replication on GPT-4o-mini, Gemini 2.0 Flash, and Llama 3.1 found much lower success when legitimate memories already existed (arXiv:2601.05504); AgentPoison and MemoryGraft generalize the technique, and delayed tool-invocation attacks against Google Gemini's memory feature planted persistent false memories that activated on trigger words. | Verify every memory/state write carries a cryptographic integrity tag bound to content, writer identity, timestamp, schema/version, and tenant or session boundary. ## Open Research Questions

- How should agent identity work for ephemeral agents that exist only for a single request? SPIFFE SVIDs with short lifetimes address this technically, but the overhead of per-request identity issuance at scale (millions of agent invocations per day) needs benchmarking beyond Microsoft's < 0.1 ms claim.
- Can agent identity be extended to include capability attestation (proving the agent is running approved code, not just that it has a valid credential)? This would address ASI10 (Rogue Agents) more directly by binding identity to verified code state.
- What is the right balance between audit completeness (logging every tool parameter) and privacy (tool parameters may contain sensitive user data)? Selective redaction of PII in audit logs while maintaining forensic value is an unsolved tension.
- How do you handle identity for agents that span trust domains (e.g., an agent that calls tools hosted by different organizations)? The Microsoft toolkit's A2A/MCP/IATP protocol bridges are an early attempt, but cross-organizational trust federation for agents lacks mature standards.
- How should trust scoring models (e.g., Microsoft's 0-1000 scale) be calibrated to avoid both false positives (legitimate agents quarantined) and false negatives (compromised agents trusted)?
- As Microsoft reports that more than 80% of Fortune 500 companies use agents built with its low-code tools, what organizational structures are needed to manage agent identity at enterprise scale -- and who owns agent credential lifecycle?
- Can blockchain-anchored audit logs provide practical tamper-evidence for multi-tenant agent deployments, or is the performance cost prohibitive? The AIVS draft's SHA-256 hash chain approach may offer a lighter-weight alternative worth evaluating against blockchain solutions.
- The IETF AIMS framework (draft-klrc-aiagent-auth) describes itself as composing existing standards rather than defining new protocols -- but does composing WIMSE + SPIFFE + OAuth 2.0 introduce integration complexity that effectively creates a new protocol in practice? Early implementation experience from organizations deploying these layered stacks would be valuable.
- How should NIST's agent identity work (the NCCoE concept paper, whose comment period closed April 2, 2026) interact with existing compliance regimes (SOC 2, ISO 27001, EU AI Act)? The mapping between NIST agent identity guidance and existing audit frameworks remains undefined.
- The "Agents of Chaos" study showed that display-name-based identity was spoofable across channels. For consumer-facing agents on platforms like Discord or Slack, where users interact via display names, what is the practical path to cryptographic identity verification without breaking the user experience?
- The OpenClaw ClawHub poisoning campaign produced hundreds of confirmed malicious skills (341 to 1,184 depending on the auditor and date), with credential theft among the payloads. How should agent skill registries implement publisher identity verification and credential isolation to prevent supply chain attacks at this scale?
- With the Unit 42 report showing identity weaknesses material in almost 90% of investigations and non-human identities often outnumbering humans, what is the right organizational model for agent credential lifecycle management -- should it sit with IAM teams, platform engineering, or a dedicated NHI function?
- CVE-2026-33017 demonstrated 20-hour time-to-exploit for an agent platform vulnerability. Given this pace, are current credential rotation schedules (requirement 9.4.3) fast enough, or do agent systems need continuous rotation with sub-hour credential lifetimes by default?
- The Meta incident, as reported, suggests that post-authentication governance is a real gap. What patterns effectively bind agent authorization to specific tool-call-level delegation scopes, rather than relying on coarse session-level permissions?
- Lab evaluations of memory poisoning (MINJA reported 98.2% average injection success) show high success rates, although a follow-up found much lower success when agents already hold legitimate memories. Can cryptographic integrity checks on persisted state (requirement 9.4.4) defend against attacks that operate through the agent's legitimate write path, or do we also need semantic validation of state changes?
- The NIST NCCoE concept paper proposes composing OAuth, SCIM, SPIFFE, and ABAC for agent identity. How much integration complexity does this introduce in practice, and are reference implementations from the NCCoE project sufficient to make this tractable for mid-size organizations?
- CVE-2026-21858 (n8n, CVSS 10.0) and CVE-2026-21992 (Oracle Identity Manager, CVSS 9.8) show that both agent platforms and identity infrastructure are high-value targets. What defense-in-depth patterns prevent a single platform compromise from cascading across all agent identities?
- CVE-2026-32211 and CVE-2026-42856 exposed that MCP's optional-auth design creates predictable authentication gaps across both vendor and open-source tool servers. Should the MCP specification mandate authentication, or is the current approach (delegating to implementations) sustainable given the growing attack surface?
- SPIFFE assigns replica-level identities by default in Kubernetes, but agents need instance-level attribution. What operational patterns make per-instance SPIFFE SVIDs tractable at scale without overwhelming SPIRE servers or policy engines?
- Hardware-anchored agent identity (Ledger's secure element approach) eliminates software credential exfiltration but introduces physical hardware dependencies. For cloud-native agent deployments with thousands of ephemeral instances, is there a middle ground between hardware-bound and pure-software identity?
- Alibaba's Open Agent Auth implements WIMSE-based three-layer identity binding. As WIMSE is still a draft specification, how should organizations manage the risk of building on pre-standard protocols that may change before ratification?
- The LiteLLM/TeamPCP attack showed that AI development libraries are now targeted for credential harvesting at massive scale (3.4M downloads/day). Should agent identity requirements extend to verifying the integrity of the agent's own runtime dependencies before credentials are provisioned?
- The CSA/Strata survey found only 23% of respondents have a formal enterprise-wide agent identity strategy and 84% doubted they could pass an agent compliance audit. Given the EU AI Act timeline (Article 50 transparency and GPAI enforcement powers from August 2026; high-risk duties deferred to December 2, 2027 by the Digital Omnibus on AI) and Colorado's January 1, 2027 effective date under [SB 26-189](https://leg.colorado.gov/bills/sb26-189), which replaced the AI Act's June 30, 2026 date, what minimum viable agent identity posture should organizations target for compliance readiness?
- Cryptographic receipt tooling (AgentMint, ArkForge, Oktsec) now makes per-action signing practically deployable. Should requirement 9.4.2's cryptographic binding be reclassified from Level 2 to Level 1, given that the tooling barrier has largely been removed?
- RSAC 2026 demonstrated that five major vendors shipped agent identity frameworks simultaneously, yet none addresses tool-call authorization, permission drift, or full decision chain reconstruction. Is the industry converging on identity as the wrong abstraction layer, when the real gap is action governance?
- The IETF dual-identity credential model (draft-ni-wimse-ai-agent-identity-02) cryptographically binds agent identity to owner identity. Does this effectively solve cross-organizational accountability, or does it create new key management complexity that limits adoption?
- With Okta reporting that 91% of organizations use agents but only 10% have a clear strategy to manage them (self-reported, method not given), what minimum viable identity posture should organizations target before deploying agents in production -- and should frameworks enforce this as a pre-deployment gate?
- Cisco's MCP gateway approach intercepts every tool call for policy enforcement. Does routing all agent traffic through a centralized gateway create a single point of failure that undermines the resilience benefits of distributed agent architectures?
- Asqav's adoption of ML-DSA-65 post-quantum signatures addresses future cryptanalytic threats, but imposes higher computational overhead than Ed25519. For high-throughput agent systems signing thousands of actions per second, is the quantum-resistance trade-off justified now, or should organizations plan a migration path from Ed25519 to post-quantum when NIST's PQC timeline firms up?
- Three IETF drafts now address agent audit (AIMS, AIVS, AAT) with overlapping but distinct scopes. Will the community converge on a single standard, or will the fragmentation itself become a compliance burden as organizations must implement multiple formats for different regulatory regimes?
- ZeroID's RFC 8693-based delegation chains with automatic scope attenuation solve the multi-hop agent authorization problem elegantly. However, token exchange adds latency at each delegation hop -- for deep agent hierarchies (5+ levels), does the cumulative overhead become a practical barrier, and what caching strategies can mitigate it without undermining revocation propagation?
- The Claw Chain attack showed that every step of a four-CVE compromise "looks like normal agent behavior" to traditional controls. Can chain-bound audit records (9.4.2) be paired with behavioral baselines to distinguish an adversary driving the agent's privileges from the agent's legitimate work, or does living-off-the-agent activity fundamentally evade action-level audit?
- Google Cloud Agent Identity demonstrates per-agent SPIFFE identity with sender-constrained, sub-day credentials inside one hyperscaler's walled garden. What is the path to equivalent guarantees for agents that span providers -- does SPIFFE federation across trust domains compose with DPoP-style token binding, or do cross-cloud agents inevitably fall back to bearer tokens at the seams?
